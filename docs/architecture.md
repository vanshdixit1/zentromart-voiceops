# Build workflow

The implementation follows the five dataset workflow actions and four capstone steps.

Text generation uses the official `google-genai` SDK with the Gemini API through Google AI Studio (`GEMINI_API_KEY`, `GEMINI_MODEL`). An optional `GEMINI_FALLBACK_API_KEY` can fail over once after a quota/rate-limit response; it must belong to a different Google project because keys in one project share quota. SDK retries are disabled so timeouts and exhausted quotas do not trigger repeated requests. The OpenAI-compatible endpoint remains optional and is used only for the existing embedding model; without its credentials, retrieval uses its existing lexical fallback.

1. **Read and validate the data.** CSV values, IDs, and pincodes remain strings. `validate_dataset.py` checks the expected core tables, advertised row counts, and the customer → orders → items → products relationships. The data dictionary remains the authority for additional columns.
2. **Build retrieval.** Markdown files are split by headings and bounded into small chunks. `[SECTION-ID]`, `doc_type`, `language`, `status`, and `effective_from` are retained as metadata. Superseded policy sections remain available for exceptions explicitly preserved by successor policies; they receive a lower ranking. Historical support logs are excluded as answer evidence. Product and pincode rows are indexed with evidence IDs. When configured, the agent embeds chunks through the OpenAI-compatible embeddings endpoint and ranks them with cosine similarity in a local in-memory vector index. Unsupported embedding endpoints fall back to offline lexical retrieval with customer-language query expansions.
3. **Connect tools safely.** The adapter imports and calls the ZIP's supplied `lookup_order` and `create_ticket` functions. An order lookup requires the caller to provide the order ID, then one proof value (last four phone digits or delivery pincode); the tool reveals no details until verification. The conversation agent allows only one retry, keeps verified state scoped to the current conversation, and redacts proof values from its history, outputs, and ticket summaries.
4. **Evaluate in stages.** The runner records generated answers, retrieved sections, reference evidence, expected decisions, required/forbidden facts, and expected tool calls. It evaluates the 52 questions, Step 3 ASR-like transcripts, and all 96 conversation turns in order with one memory instance per conversation. Compare Step 1 and Step 2 on the same questions; use the generated summary as a screening report and review language/date paraphrases manually.
5. **Add speech.** The Gnani adapter is lazy-loaded, requires `GNANI_API_KEY`, and makes no call to another speech service. STT language is selectable per call. TTS always names the configured model and voice. The adapter follows the official [STT Python SDK](https://docs.gnani.ai/api/STT/speech-to-text) and [TTS Python SDK](https://docs.gnani.ai/api/TTS/tts-inference): transcription returns a transcript dictionary, while synthesis returns audio bytes that are written to the requested WAV path. Batch output includes transcript, text answer, source IDs, and speech output.

The course reference date is 20 October 2026. Calendar-day returns and business-day delivery estimates are intentionally distinct; business days run Monday through Saturday and skip dates in `holidays.csv`.
